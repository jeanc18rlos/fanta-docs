Fantaisa treats finishing a design like merging code: **review before save.**
A deterministic audit runs first, you read it (optionally with an annotated
screenshot), and revisions flow through a PR-style comment → consolidate →
commit loop.

## `review_design`

`review_design` is a **deterministic audit** — same input, same verdict — run
before finalizing. It returns issues, warnings, and passes, plus per-section
scorecards, and can attach an annotated screenshot.

It checks, at minimum:

- **Hierarchy** — loose children directly on the page (not inside a frame).
- **Spacing / gutters** — gaps below the minimum (default **96**).
- **Overlap** — pairwise overlap between nodes that should not collide.
- **Component reuse** — repeated structure that should be a component instance.
- **Design-token coverage** — fills/spacing/text that bypass tokens.
- **Text overflow / contrast** — clipped labels and low-contrast text.
- **Empty sections** — frames that ended up with no content.

### Scorecard shape

The result is structured so an agent can act on it and a human can scan it:

```json title="review_design — result"
{
  "issues": [
    { "kind": "overlap", "nodes": ["card-2", "card-3"], "detail": "12px overlap" },
    { "kind": "loose_child", "node": "title", "detail": "page child not in a frame" }
  ],
  "warnings": [
    { "kind": "gutter", "node": "row-1", "detail": "gap 64 < min 96" },
    { "kind": "token", "node": "badge", "detail": "raw fill #1A1A1A bypasses tokens" }
  ],
  "passes": ["text-contrast", "no-empty-sections", "component-reuse"],
  "scorecards": [
    { "section": "Pricing", "score": 82, "issues": 1, "warnings": 1 },
    { "section": "Footer",  "score": 95, "issues": 0, "warnings": 0 }
  ],
  "screenshot": "review-annotated.png"
}
```

<Callout type="info">
Pass the option to attach an annotated screenshot and the audit marks each
flagged node visually — the fastest way to see *where* a gutter or overlap
problem lives, not just that it exists.
</Callout>

## Review before save

Make the audit a gate, not an afterthought. The canonical loop ends with
verify → save, and `review_design` is the verify step that decides whether the
work is ready:

```text title="Gate the save on the review"
build / revise
export_png   { node: <frame> }
review_design                  # read issues + scorecards
# fix issues, re-run, repeat until clean enough
save_document
```

## The PR-style revision loop

Revisions are handled like a pull request, so feedback is explicit and the
history is legible:

1. **Comment.** Pin comments on the surface where something needs to change —
   each pin is a concrete, located request, like a line comment in a PR.
2. **Consolidate.** When you say "consolidate," the agent gathers the pinned
   comments and the review findings and applies them in one pass.
3. **Commit.** The consolidated revision is saved as the next version, so the
   change log reads as a sequence of reviewed revisions rather than a blur of
   edits.

<Callout type="warn">
Don't skip the review to "save time." An unaudited save is how loose children,
sub-minimum gutters, and token-bypassing fills slip into a document — exactly
the issues `review_design` is built to catch.
</Callout>
