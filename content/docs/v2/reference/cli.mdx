From the [fanta-edit repository](https://github.com/jeanc18rlos/fanta-edit):

| Command | Purpose |
| --- | --- |
| `cargo run -p fanta` | Build and run the current app package; plain `cargo run` also works because `fanta` is the workspace default. |
| `cargo build --release -p fanta` | Build `target/release/fanta`. |
| `./script/bundle-mac` | Package the macOS app and DMG. |
| `.\script\bundle-windows.ps1 -Architecture x86_64` | On Windows, build the app, CLI, update helper, and an unsigned local Inno Setup installer by default. |
| `./script/clippy` | Repository lint workflow. |
| `script/smoke-mcp <fanta-binary> <project-dir>` | Exercise the live MCP/design loop against a running app. |

With a project open in a non-Store Fanta build, choose **Connect External Agent** in Fanta. It copies project-scoped Codex and Claude Code instructions with the running app's actual executable and user-data directory. The Claude Code command has this shape:

```bash
claude mcp add --scope project --transport stdio fanta -- /Applications/Fanta.app/Contents/MacOS/fanta --mcp-stdio --user-data-dir '<Fanta data directory>'
```

Use the copied command verbatim so the instance path is correct. For Codex, Fanta provides a `[mcp_servers.fanta]` snippet for the trusted project's `.codex/config.toml`. The bridge requires a running app and focused design. `fanta_live_mcp.enabled` defaults to true in user settings. There is no `FANTA_MCP_ADDR` or `fanta-mcp` binary in this checkout. The packaged Mac App Store bridge has not been verified; its in-app local MCP subprocesses are disabled.

The same `--mcp-stdio` switch is compiled on Windows. From a Windows source build, point an external MCP client at `target\debug\fanta.exe --mcp-stdio` while the editor is running with a design focused. The Windows bridge uses an AF_UNIX socket, which requires Windows 10 version 1803 or later. This source path is separate from any public Windows installer.

## Static website export

The source repository includes a `fanta-site` CLI for a saved Fanta project. It needs a matching, separately built Fanta-JS `packages/runtime` directory; point `--runtime` at that directory. The output is a static, read-only site with one URL per design page, page navigation, pan, and zoom. It does not play prototype interactions or motion, and the CLI does not deploy the site.

```bash
cargo run --locked -p fanta-site -- \
  "/path/to/My Design" "/path/to/site-output" \
  --runtime "/path/to/Fanta-JS/packages/runtime" --offline
```

The output directory must be empty or an earlier Fanta site export. See [website export](/docs/v2/formats/website-export) for the required runtime files, font choices, and hosting steps.

## Compile a runtime bundle

The source also provides `fanta-compile`, which compiles a saved project to one `program.fanta` bundle containing the document, assets, and embedded fonts. This is a derived runtime file for a player or website, not the editable project or a visual export command in the app. The WebAssembly `fanta-runtime` package loads it through `loadBundle`; it does not parse FNX or FSS source in the browser.

```bash
cargo run --locked -p fanta-site --bin fanta-compile -- \
  "/path/to/My Design" "/path/to/dist/program.fanta" --offline
```

The project path contains `fanta.json`. As with website export, use repeatable `--font-dir` options for licensed font files or `--substitute "Brand Font=Source Sans 3"` for a replacement. `--offline` prevents font downloads. The compiler checks that every page loads in the native runtime before writing the bundle. Recompile when the project changes; a runtime rejects a bundle from a newer document schema. The command and bundle format are in the [committed source guide](https://github.com/jeanc18rlos/fanta-edit/blob/d4fe64713e8615607878d896049f88379e7cc39f/docs/fanta/runtime-bundle.md).

## Deep links

Fanta 2.0 registers `fanta://` app links. Fanta 1.0 registered `zed://`, so update saved links when you move from 1.0.
