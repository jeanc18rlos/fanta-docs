---
title: Architecture
description: How Fanta’s app shell, design engine, source files, and MCP connect.
---

Fanta’s desktop executable is built by the `fanta` Cargo package and named `fanta`. `fig_viewer` connects the design UI, canvas, project persistence, and local MCP server to the design engine. The source declares version 2.0.0, which has no installer yet.

| Area | Source |
| --- | --- |
| App shell and executable | `crates/fanta` |
| Design UI, source reload, export, MCP | `crates/fig_viewer` |
| Agent operation types and guidelines | `crates/fanta-design-ops`, re-exported by the app's agent seam `crates/design_surface` |
| Project loading, layout, comments, screenshots, and saving without the app | `crates/fanta-headless`, shared by the editor |
| Source-only Rust Design API for sessions, nodes, templates, and export | `crates/fanta-api` (unpublished; no packaged language binding) |
| Local engine runner (cloud integration in development) | `crates/fanta-engine` |
| Scene graph and edit operations | `crates/fanta-doc` |
| `.fnx` parser and printer | `crates/fanta-fnx` |
| Project layout and `.fant` format | `crates/fanta-format` |
| Figma import | `crates/fanta-fig-interop` |
| Canvas, rendering, text, human tools | `fanta-canvas`, `fanta-render`, `fanta-text`, `fanta-tools` |
| Presentation engine | `crates/fanta-present` |
| Native compiler for FNX and project sources | `crates/fanta-format/src/runtime.rs` |
| Checksummed compiled bundle format | `crates/fanta-bundle` |
| Native/WebAssembly playback of a compiled bundle | `crates/fanta-runtime` |
| Bundle and static website export commands | `crates/fanta-site` (website export requires a separately built matching runtime package from Fanta-JS) |

A project contains `fanta.json`, `.fnx` source under `pages/` and `components/`, managed JSON metadata, assets, an `AGENTS.md` seed, and a `fanta.md` design specification. Layout v5 stores a variant set in `components/<set>/set.json` with each member in a child folder; standalone components keep their own component folder. The reader accepts v4 sets and migrates them on the next save. Canvas operations autosave to source; valid source changes reload the canvas; Git tracks the folder. The Code workspace validates the active page or component's FNX and paired JSON against the project before writing them. Structural canvas saves retain supported authored FNX fields and comments on surviving nodes; a lossy destructive change reports a preservation error instead of silently rewriting the source.

The external MCP server runs in the app over a private Unix socket. `fanta --mcp-stdio` discovers the socket and bridges a client to the focused design. It registers 14 tools, including `add_comment`, through the shared `design_surface` provider; `batch_design` streams 44 typed `DesignOp` values. Content edits form one undoable transaction and roll back if an operation fails; selection and viewport changes are not transactional. `batch_get` projects requested nodes as a summary, editable style, or raw data; raw requires exact node IDs. The bridge can receive `--user-data-dir` to target the running instance. The older `fanta-app` / `fanta-ai` crate map and fixed HTTP port do not describe this checkout.

The native `fanta-format` compiler turns a saved project into a `fanta-bundle` program with a compiled document, assets, and fonts. `fanta-compile` writes this as `program.fanta`; `fanta-runtime` loads the compiled bundle rather than parsing FNX in the player. The separate `fanta-site` command packages the same bundle with an explicitly supplied matching Fanta-JS runtime into a read-only static site. Its generated viewer offers page navigation, pan, and zoom; it does not play prototype interactions or motion. A custom page using the runtime can drive those interactions, as the source auth-wizard sample demonstrates. Source tests cover the Rust compile and playback paths, while public browser and installer acceptance for v2 remain separate. [Runtime bundle →](/docs/v2/formats/runtime-bundle)

`fanta-api` runs on `fanta-headless` without opening the app. It provides a Rust `DesignSession` for in-memory, project-folder, or `.fant` designs, typed node edits, undo steps, polled events, template filling, and visual export. It is part of the repository and has not been published as a crate or wrapped for Node. [Rust Design API →](/docs/v2/reference/design-api)

The engine's implemented command runs an ordered request file against a local project directory, using this headless path for template filling and batch PNG export. Its source contains a contract for a GitHub-backed HTTP worker and v2 service routes, but the binary has no HTTP server and explicitly rejects GitHub sources. Treat the contract as a future integration design rather than an available network API.
